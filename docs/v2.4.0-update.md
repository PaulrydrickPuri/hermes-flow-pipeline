## 2. `flow-decide` — what was added

The decide phase gained a YAGNI reflex at both points where it commits to
something.

### 2.1 Step 2 — Brainstorm: an option set must include doing nothing

> **Where the ponytail pack is present, invoke `/ponytail` before settling the option set.**
> Every option set must then contain a *do nothing* / *the smallest thing* option, because
> rung 1 of its ladder is *does this need to exist at all?* A brainstorm with no YAGNI option
> has not considered the first rung — name it among the rejected alternatives and say why it
> lost.

Scoped explicitly: pack present on `architect`, `planner`, `builder`, `codemax`,
the root tree; **absent on `decider` and `doubter`**.

### 2.2 Step 3 — Plan: cut the task list the way you cut code

> **Where the pack is present, apply `/ponytail` to the task list**: cut tasks the way you
> cut code — the fewest tasks that satisfy the criteria, and the laziest design that works. A task that exists "for later"
> is the planning form of scaffolding — rung 1 applies. Being lazy here shortens the
> solution, never the reading: the *verifiable criterion* rule above still binds every
> task that survives.

The last sentence is the guard: laziness shortens the solution, **never the
reading**.

### 2.3 The placement map — so it is not re-litigated

A new section fixes a home for all six ponytail skills, or records that they have
none:

| Skill | Where it belongs | Why |
|---|---|---|
| `/ponytail` | decide Step 2 (options) + Step 3 (task cut); build Step 1 + Step 3 | the core rule — a reflex at decide time, not only at code time |
| `/ponytail-review` | build Step 3 (simplify) | the defined over-engineering pass on your own diff |
| `/ponytail-debt` | build Step 3, counted ledger | the only per-repo figure the pack authorises |
| `/ponytail-gain` | build Step 7 report, as a **labelled benchmark card** | its own text forbids a per-repo savings number |
| `/ponytail-audit` | **nowhere** — on-demand / scheduled hygiene | whole-repo scope, not diff scope; it would blur Step 3 |
| `/ponytail-help` | operator reference card | one-shot display, not a mode |

### 2.4 A bounded verification budget

> "Verify every number you change", with no stop condition, becomes an unbounded research spiral: one run
> spent 2 hours generating 7 scratch scripts, re-opening settled questions while its deliverable sat
> untouched. Bound it:
> - verify only what a finding requires, then stop;
> - if a sweep suggests a pin should change, record it as an **OPEN QUESTION for the doubt gate** instead of
>   re-pinning — the gate owns adversarial re-examination, and a planner that re-verifies without limit is a
>   cost centre, not a safeguard.

The motivating incident is stated in the text rather than hidden: a planner run
that burned two hours on scratch scripts while the deliverable sat untouched.

### 2.5 New red flag

> ❌ A brainstorm with no *do nothing* / *smallest thing* option where the pack is present

## 3. `flow-build` — what was added

### 3.1 Step 1 — the gate outranks the rule

> **Where the pack is present, `/ponytail` applies to the implementation too — but it never
> outranks this gate**, and the pack says so itself: *"Never a reason to skip gates: the rule
> trades less code for more thinking, not for skipped tests."* TDD's RED gate wins every time.
> If a "lazier" solution cannot be expressed as a failing test first, it is not the lazier
> solution; it is an untested one.

This is the precedence rule the whole update turns on: ponytail can change *what*
gets built, never *whether the test came first*.

### 3.2 Step 3 — Simplify, rewritten around a real procedure

The step was rewritten rather than extended. Before, it told the operator to copy
`/simplify-code` into the tree **first** and asserted that the skill "exists only
on the `default` profile, and neither `codemax` nor any bot profile ships it" —
which was **measurably backwards** (it is live on `builder`, archived on the root
tree) and contradicted the surrounding paragraph.

Now:

> **Where the ponytail pack is present**, apply `/ponytail` to your own diff first — climb the
> ladder against code you just wrote … — then invoke `/ponytail-review` on the same diff.
> …
> **Where `/simplify-code` resolves**, it also runs, and it runs **first** — it is the
> broader pass (dead code, duplication, speculative abstraction), so let it work before the
> ponytail pass looks specifically for over-engineering.

Availability is recorded as measured (§4), with the earlier false claim named and
corrected in place instead of silently dropped.

**The counted ledger** was added as the only authorised per-repo figure:

```
grep -rnE '(#|//) ?ponytail:' .
```

> Report `<N> markers, <M> with no trigger.` A clean ledger reports
> `No ponytail: debt. Clean ledger.` — that is a legitimate outcome, not a failure.

### 3.3 Step 6 — a second lens was considered and is **not** adopted

> **No ponytail pass here.** A second over-engineering lens at Step 6 was considered and is
> **not adopted** — the pack's pass lives at Step 3, where the code is still being shaped.
> `/code-review` at this step is unchanged.

Recorded because a considered-then-rejected proposal is exactly what gets
re-opened six months later.

### 3.4 Step 7 — the report line, and the honesty boundary on numbers

The report block gained:

```
Simplify:  /ponytail-review: [N] cuts  |  debt: [N] markers, [M] no-trigger
```

and `/ponytail-gain` is explicitly limited:

> So the gain card may appear in the report only as a **labelled benchmark card**; it must
> never be turned into "this build saved X lines/tokens". The unbuilt version was never
> written, so there is no baseline to subtract from.

### 3.5 Budget — measured, not guessed

> A real 13-task build (logic core -> rendering -> evidence harness) consumed **150 tool calls** and hit the
> agent turn budget *before* `/simplify-code` and `/code-review` could run. Two rules follow:
> - **Raise the budget before a long build:** `hermes -p <bot> config set agent.max_turns 300` (the measured
>   build needed more than 150; the setting is per-profile, so set it on the builder only).
> - **If it still runs out, finish the remaining quality steps as a SECOND PASS** on the same plan — never
>   skip them silently. Report which steps did not run. A stopped run that says what it did not do is worth
>   far more than one that implies completeness.

This one comes straight from an observed failure: the run truncated at the turn
cap and never reached its last two quality steps. The rule is "raise the cap, and
if it still runs out, say so" — not "trust that it finished".

### 3.6 New red flags

> ❌ Letting the ponytail rule past a gate — it never outranks TDD's RED gate
> ❌ Printing a per-repo savings number from `/ponytail-gain` (benchmark medians only)

## 6. How to re-verify all of this

```bash
bash evidence/verify.sh              # report + checks; exit 1 if any check FAILs
bash evidence/verify.sh --selftest   # prove each check can fail
```

The six checks and what they assert:

| Check | Assertion | Live result 2026-09-29 |
|---|---|---|
| A | flow pair present in all 7 trees | PASS |
| B | all 7 flow-build copies byte-identical | PASS |
| C | all 7 flow-decide copies byte-identical | PASS |
| D | no tree has a partial ponytail pack | PASS |
| E | ponytail absent on both judging roles | PASS |
| F | pipeline doc's v2.4.0 sections in all 7 trees | **FAIL** (real, open — see known-gaps) |

`--selftest` builds a clean scratch tree, confirms all six checks pass there,
then injects one specific defect per check and confirms **each check flips to
FAIL**. Without that, a check that can never fail would look identical to a check
that is genuinely clean:

```
=== SELFTEST 0: clean scratch tree — every check must PASS ===
  clean-tree failures: 0 (want 0)
=== SELFTEST 1: delete a tree's flow pair (check A must FAIL) ===
FAIL  A. flow pair present in all 7 trees          got=6 want=7
...
RESULT: every check is both satisfiable and fail-able.
```

## 8. One caveat about the baseline

The pre-change baseline is a **backup directory**, not a git commit: the wrappers
live as unversioned profile config under `~/.hermes/**`, so a backup file is what
substitutes for a diff. Consequences, stated plainly:

- `evidence/verify.sh` reports `BASELINE MISSING` and stops the delta section if
  that directory is gone — the "what changed" claim becomes unverifiable rather
  than silently absent.
- The diffs in `evidence/` are copies of what the harness regenerates; if the
  baseline is deleted they cannot be regenerated, only read.
